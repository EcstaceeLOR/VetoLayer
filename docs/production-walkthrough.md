# VetoLayer judge production walkthrough

Target length: **2–3 minutes**.

The presentation should prove one thing clearly:

> **An autonomous agent can have permission to act and still need contextual judgment before the action is safe to execute.**

The presentation uses the **real product workflow** from start to finish.

## Before recording or presenting

Prepare one real presentation workspace/project/environment on the latest verified production deployment:

- one active deterministic policy;
- one active SERV-contextual policy for the emergency-deployment exception;
- one action that will enter `REVIEW` because required approval evidence is missing;
- one Human Review case generated by that decision;
- a reviewer identity that can add the missing approval/evidence;
- one Decision Receipt from the first evaluation and the ability to inspect the re-evaluation receipt.

Do not stage credentials, API keys, webhook secrets, private user data, or unrelated production information in the presentation workspace.

## 0:00–0:20 — The problem

Open the VetoLayer landing page, then the authenticated Control Center.

Say:

> Autonomous agents are getting authority to merge code, deploy production, issue refunds, and call high-impact tools. Access control can tell us whether an agent *can* act. VetoLayer asks whether it *should* act right now, given policy, evidence, exceptions, and context.

Point out the active workspace/project/environment scope.

## 0:20–0:45 — The policy boundary

Open **Policy Studio** and show the two-layer model:

- a deterministic rule for hard facts/restrictions;
- a contextual policy whose exception requires judgment over incident evidence, checks, and human approval.

Say:

> Hard facts stay deterministic. SERV is used only where the policy actually requires interpretation. SERV can recommend an outcome, but it cannot override a deterministic hard block.

Show the human-readable lifecycle/version surface and move on.

## 0:45–1:15 — Proposed action → REVIEW

Submit or open the prepared high-impact action:

- autonomous coding agent proposes an auth/security production deployment;
- restricted deployment window is active;
- critical incident is verified;
- security checks pass;
- security-lead approval is missing.

Show the resulting Decision Receipt / Decision Explorer detail.

Expected result: **`REVIEW`**.

Point out:

1. exact policy versions evaluated;
2. deterministic findings;
3. SERV/contextual findings;
4. the missing approval/evidence;
5. provider status / reasoning trace;
6. integrity verification.

Key line:

> VetoLayer did not decide that the agent lacked permission. It decided that the available evidence was not yet sufficient to justify the exception.

If provider status is fallback, say so and keep the result as `REVIEW`; never present fallback as successful SERV reasoning.

## 1:15–1:45 — Human Review becomes evidence

Open the exact case in **Human Review**.

Add the required reviewer evidence/approval through the product workflow, then resolve/re-evaluate.

Say:

> Human review is not a bypass switch. The reviewer action becomes evidence, and VetoLayer re-runs the same policy + SERV + orchestrator path.

Show that the re-evaluation creates a **new Decision Receipt** with parent lineage back to the first receipt.

Expected result when every exception requirement is satisfied: **`ALLOW`**.

The action itself should be the same action; the material change is the new verified evidence.

## 1:45–2:15 — Prove the system is operational

Show two or three of these, quickly:

- **Decision Explorer / Receipt Center** — search, lineage, comparison, integrity verification;
- **Operational Analytics** — real outcome/review/evidence/SERV metrics;
- **Developer Console** — API key/webhook/request tester without exposing any credential value;
- **Integrations** — GitHub App or Developer API readiness;
- **Audit** — append-only actor/action history;
- **Notifications** — review alert/deep-link delivery.

Say:

> The decision engine is surrounded by the operational product teams need to run governed agents continuously.

## 2:15–2:40 — Why SERV matters

Return to the first or second receipt and point to the contextual finding.

Say:

> SERV is doing structured contextual judgment over policy intent, exceptions, evidence, contradictions, and missing information. Deterministic restrictions stay deterministic, and malformed or unavailable SERV output fails safely to REVIEW.

Mention that Chrome E2E deliberately forces SERV network failure and asserts that the real Developer API returns `REVIEW`, never fail-open `ALLOW`.

## 2:40–3:00 — Close on market + proof

End on the new receipt or Control Center.

Say:

> VetoLayer is the decision layer between agent intelligence and real-world authority: deterministic where the answer is deterministic, SERV-powered where judgment is required, and auditable either way. We start with coding and deployment agents, then expand the same policy-and-evidence model into support, procurement, finance, and operations.

Optional final line:

> Every release is gated by repository cleanliness, lint, typecheck, full tests, a production build, real Chrome E2E, browser artifacts, release smoke, and a separate deployed-production smoke workflow.

## Presentation integrity rules

- Use the latest production deployment that passed Production Smoke.
- Do not claim a live SERV result when provider status is fallback.
- Do not describe the receipt hash as blockchain notarization, legal certification, or cryptographic immutability.
- Do not claim VetoLayer replaces IAM, authorization, security review, or compliance tooling.
- Do not expose GitHub, SERV, Supabase, webhook, worker, or VetoLayer API credentials in screenshots/network panels.
- Do not use unrelated personal or customer data in the presentation workspace.
- Keep the core story on one action so the `REVIEW → evidence → re-evaluation → new receipt` lineage is obvious.
